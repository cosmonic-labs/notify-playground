These are the shapes cosmonic:notify can express. Loading one fills in every control below, so the fastest way to build your own is to start from the closest one and edit it. In the source they are a single array at the top of src/index.html — add an object, get a button.

the notification

urgency is honoured where the platform has the concept. GNOME maps it to the freedesktop urgency hint; Windows maps critical to the urgent toast scenario and low to silent; macOS has no real equivalent, so capabilities().urgency is false there and the host drops it rather than pretending.

The urgency lesson, learned on GNOME: a non-critical notification is settled the moment its banner fades — a few seconds in, reason "expired", and a click on whatever remains in the tray goes nowhere. If you are asking a question (buttons, reply), send it as critical so it stays on screen until answered; normal is for information. And timeout-ms: 0 means the host default, never "expire immediately" — the freedesktop convention.

buttons

A button's target is what the host does when it is clicked. callback just returns the answer to the component; url opens a link (http/https only — anything else is rejected); deep-link opens Cosmonic Desktop at a relative route. Either way the component still learns which button was pressed.

inline reply

Windows and macOS render a real text box. GNOME does not — so the host degrades this to an ordinary button carrying the same id, and the component receives action("reason") instead of reply("reason", …). That is the whole degradation story: you always learn the user started a reply.

fire it

post returns an id immediately; the answer shows up in the feed below when events.pull next runs. request does not return until the user answers — the HTTP request in front of it stays open for exactly as long as the human takes. Both are the same notification; only the delivery differs.

          Why can't this page just do it? The daemon's control API listens on a unix
          socket with no TCP bind at all, and a component has no way to reach it — the
          notification interface is the only channel between a component and the
          daemon here. That is deliberate: a component that could call the control API
          could run arbitrary workloads and resolve secrets. So simulated responses come
          from your terminal, not from the sandbox.

calling back into cosmonic — the target menu

    

      Every button (and the notification body) carries an action-target. A
      deep-link reopens Cosmonic Desktop at an app route — the host opens
      cosmonic://navigate/<route>, and the app acts only on routes it
      recognises; anything else just focuses the window (fail closed, on top of the daemon's
      own validation). Each button here fires one toast exercising exactly one target kind:
      act on the toast, then watch the feed.

      The free one: a body click with no explicit default_target gets the
      host default — a deep-link to this workload's own page
      (workloads/<ns>/<name>), composed by the host from the workload
      identity, never from component input. The refused group sends targets the daemon
      must reject — relative paths only: no scheme, no leading slash, no .., no
      query or fragment — so nothing is shown at all; the point is watching the refusal land
      in the feed before a toast ever exists.
